# 班前会模块全量梳理

## 1. 文档说明

- 文档目标：抽取当前系统中与“班前会 / 班前会议 / 会议签到 / 安全交底 / 会议纪要 / 会议统计”相关的页面、组件、字段、状态、交互和旁路依赖，形成一份可用于业务理解、方案设计、接口对接和二次开发的基础文档。
- 抽取范围：当前前端仓库 `project-ai-web` 中已经实现、引用或以 mock 形式出现的班前会相关内容。
- 统计口径：以源码现状为准，不对业务正确性做额外假设。
- 当前结论：班前会模块已经具备“会议管理 + 我的待办 + 安全交底 + 会议签到一体机 + 纪要展示 + 统计看板引用”的雏形，但数据模型、状态口径和接口实现仍然明显分裂。

## 2. 业务定位

### 2.1 产品口径

- 在 `项目功能清单.txt` 中，班前会系统被归类到安全生产管理业务下，功能描述包含：
  - 会议管理
  - 参会考勤
  - 会议内容与纪要
  - 会议统计
- 在 `src/views/function-introduce/data.ts` 中，班前会系统被描述为安全生产数字化管理平台的重要组成部分，与风险分级、隐患治理、特殊作业、设备状态分析等能力联动。

### 2.2 菜单与路由入口

## 4. 业务链路梳理

当前源码体现出的班前会主链路如下：

1. 管理员在“会议管理”中新建班前会。
2. 录入会议基础信息、参会人员、议程、准备事项和注意事项。
3. 管理员发起会议。
4. 参会人员在“班前会系统”中看到自己的待办。
5. 参会人员完成以下待办动作：
   - 会议签到
   - 确认安全措施
   - 签署安全承诺书
   - 参与安全交底
6. 会后在会议纪要中沉淀参会清单、风险点明细、设备检查、签署情况、异议反馈、附件。
7. 最终结果进入统计分析，体现在班前会召开率、参会率、召开质量分析等看板数据中。

## 5. 页面功能与动作清单

### 5.1 `/shift-meeting` 班前会系统

主要功能：

- 会议待办列表展示
- 按会议名称、班组、紧急程度、待办类型、时间范围、交底状态筛选
- 查看会议详情
- 打开安全交底表单
- 会议签到
- 安全措施确认
- 签署安全承诺书

当前动作：

| 动作 | 说明 |
| --- | --- |
| `detail` | 打开交底详情弹窗 |
| `briefing` | 打开安全交底表单 |
| `sign` | 打开签到弹窗并生成 4 位签到码 |
| `confirmMeasures` | 打开安全措施确认弹窗 |
| `signPromise` | 打开安全承诺书签署弹窗 |

### 5.2 `/meeting-management` 会议管理

主要功能：

- 列表查看会议
- 查询筛选
- 新建会议
- 编辑会议
- 发起会议
- 取消会议
- 上传会议材料
- 查看会议详情
- 查看会议纪要

当前动作：

| 动作 | 可见条件 | 说明 |
| --- | --- | --- |
| `detail` | 全部 | 查看会议详情 |
| `launch` | `pending` | 发起会议 |
| `upload` | `pending` / `in_progress` / `completed` | 上传会议文件 |
| `viewMinutes` | `completed` | 查看会议纪要 |
| `edit` | `draft` / `pending` | 编辑会议 |
| `cancel` | `draft` / `pending` | 取消会议 |

### 5.3 `/all-in-one` 会议签到一体机

主要功能：

- 现场显示签到状态
- 展示签到记录
- 进入多维识别签到
- 多维识别完成后展示异常结果

多维识别步骤：

1. 人脸
2. 证书
3. 工牌
4. 体温
5. 状态

## 8. 当前实现差异与问题

### 8.1 数据模型分裂

当前至少存在三套班前会模型：

1. 会议管理模型
   - `start_time`
   - `area_name`
   - `expected_attendees`
   - `actual_attendees`
   - `risk_level`
   - `attendees`
2. 班前会待办模型
   - `meeting_time`
   - `region_name`
   - `attendance`
   - `todo_type`
   - `briefing_status`
3. API mock 模型
   - `meeting_time`
   - `region_id`
   - `attendance`
   - `participants`
   - `task_content`
   - `status: 0~4`

这三套模型的字段命名、状态枚举和业务边界都不一致。

### 8.2 接口文件缺失

- `shiftMeeting.vue` 导入了 `@/api/safeProManager/meetingBriefing`，但仓库内不存在该文件。
- `approval.vue` 导入了 `@/api/safeProManager/approval`，但仓库内不存在该文件。
- 相关页面因此在文件内部重新定义了 mock 函数，形成“页面本地 mock”和“api 目录 mock”并存的状态。

### 8.3 状态机不统一

- 管理页认为 `pending` 状态可以发起会议。
- API mock 中 `startMeeting` 只允许 `0=未发起` 变成 `1=待召开`。
- 表单新建会议时又会根据时间差直接给出 `pending` 或 `in_progress`。

说明当前“未发起 / 待召开 / 待发起 / 进行中”的口径并未统一。

### 8.4 一体机链路未接真实会议

当前 `/all-in-one` 一体机页面具备界面和流程，但数据基本都是前端写死：

- 时间
- 设备状态
- 签到人数
- 签到记录
- 识别对象
- 检测结果

它更像独立演示页，尚未真正与班前会会议主数据联动。

### 8.5 审批模块挂靠但未专用化

`/approval` 虽然位于“班前会议 -> 我的待办”下，但当前审批类型、字段和流程并非围绕班前会专门设计，更像公共审批样板页。

## 9. 推荐的后续收敛方向

如果后续要继续做班前会业务，建议按以下顺序推进：

1. 统一主数据模型
   - 确定会议主表字段
   - 统一 `meeting_time/start_time`、`region/area`、`participants/attendees` 等命名
2. 统一状态机
   - 明确定义草稿、未发起、待召开、进行中、已完成、已取消
3. 明确待办子流程
   - 签到
   - 措施确认
   - 承诺签署
   - 安全交底
4. 将一体机考勤与会议主数据打通
5. 将纪要、统计、审批、任务分配统一挂到同一会议实体之下
